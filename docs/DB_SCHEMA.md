# Database Schema — Guardianes de Arequipa

> Schema: `public`. 12 tables, 1 view, 1 trigger, 1 auth hook. Supabase PostgreSQL.

## Entity-Relationship (key FK chains)

```
usuarios ──→ teams ──→ schools
  │            │
  │            └──→ levels (level FK)
  └──→ roles
    
chapters ──→ fragments
  │
  └──→ missions ──→ mission_questions
  │                    │
  └──→ teams (current_chapter_id)

mission_progression ──→ teams
                  ├──→ missions
                  └──→ mission_questions (assigned variant)
```

## View: `vista_equipos_completos`

Denormalized team view used by student/leader panels. GRANT SELECT to `authenticated` and `anon`.

```sql
SELECT
  t.id            AS team_id,
  t.name          AS team_name,
  t.level,
  l.title         AS level_title,
  l.next_level_points,
  t.points,
  t.color,
  t.school_id,
  s.name          AS school_name,
  members_json,       -- json_agg of {id, name, alias} from usuarios WHERE team_id = t.id
  earned_fragments    -- json_agg of fragment ids WHERE required_level < t.level
FROM teams t
JOIN schools s ON t.school_id = s.id
LEFT JOIN levels l ON l.level = t.level
```

## Trigger: `trigger_mision_completada`

Fires AFTER UPDATE on `mission_progression` when `status` changes to `'completed'`:

1. Reads mission `points` from `missions` table
2. Updates `teams`: `missions_completed += 1`, `points += mission_points`, `last_completed_at = now()`
3. If `points >= next_level_points`: `level += 1`, `next_level_points += 1500`
4. Updates `schools`: same increments + `last_completed_at = now()`

**Do NOT update points manually** — this trigger handles all point accumulation.

## Auth Hook: `custom_access_token_hook`

SECURITY DEFINER function that runs on every login/refresh. Injects into JWT claims:
- `role_id` (uuid) — from `usuarios.role_id`
- `team_id` (bigint) — from `usuarios.team_id`

Used by RLS policies for row-level access control. Has exception handler: if it fails, returns original event (does not block login).

## RLS Summary

| Table | Policy | Effect |
|-------|--------|--------|
| `schools`, `teams`, `chapters`, `fragments`, `missions`, `mission_questions`, `insignia`, `levels` | Public read | All users (even anonymous) can SELECT |
| `usuarios` | Own profile | Authenticated users see own row; public sees all |
| `mission_progression` | Public read + role-gated write | Anyone can SELECT; students (role_id `11111…`) can INSERT/UPDATE their own team's rows; leaders (`22222…`) and admin (`44444…`) can UPDATE any team's rows |
| `app_settings` | Public read, admin-only write | `role_id = 44444444-4444-4444-4444-444444444444` |
| `team_insignia` | Public read | Anyone can SELECT |

Role UUIDs in JWT are compared against fixed UUIDs in policies. The `role_id` is injected by `custom_access_token_hook`.

## Ranking order (tiebreaker)

All rank queries order by: `points DESC, last_completed_at ASC NULLS LAST`.

A school/team with 0 points gets `rankingPosition = null` (shown as "—" in UI). Only schools with `points > 0` get a position.
